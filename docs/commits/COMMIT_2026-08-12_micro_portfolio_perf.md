perf(micro/portfolio): 정밀검사·포트폴리오 병목 제거 — 매도레이더 111.67초 → 3.40초

계측으로 병목을 특정한 뒤 순차 I/O 병렬화와 중복 계산 제거를 적용했다.
`app.py` 단일 파일 변경이며 공유 코어 모듈·자동화는 건드리지 않았다.

---

## 1. 계측 인프라 (선행 작업)

추측으로 세 번 오진한 뒤 계측을 먼저 심는 방식으로 전환했다. 결과적으로
매번 숫자가 나오자마자 원인이 확정됐다.

**(A) 통계 저장소를 `@st.cache_resource` 로 이관 — 계측 자체의 버그였음**

`_FMP_STATS` 를 모듈 레벨 dict 로 뒀는데, `app.py` 는 Streamlit 스크립트
본체라 **리런마다 재실행되어 카운터가 매번 0으로 초기화**됐다. Sheets 통계는
`session_state` 라 살아남았고 FMP 만 죽어 "항상 0"으로 보였다.
`cache_resource` 는 리런 간 같은 객체를 돌려주므로 누적이 유지된다.
세션이 아니라 프로세스 단위인 것은 의도다 — 워커 스레드에서도 접근해야 한다.

**(B) `_timed` 컨텍스트 매니저 — 구간별 소요 시간 + FMP 콜 수**

시간만으로는 "네트워크인가 CPU인가"를 가를 수 없다. 진입/이탈 시점의 전역
FMP 카운터 차이로 구간별 호출 수를 함께 센다. 패널 하단에 **미계측 콜 수**를
표시해 아직 못 잡은 영역이 얼마인지 드러낸다.

**(C) 렌더 순서 안내**

사이드바는 본문보다 먼저 그려지므로 방금 실행한 동작의 수치는 화면을 한 번
더 갱신해야 반영된다. 패널에 명시했다.

계측 구간 19개(정밀검사 12 · 워치리스트 5 · 포트폴리오 3)를 배선했다.

## 2. 정밀검사 탭

**(A) 합류점수 부가지표 — 5개 조회 병렬화** `3.27초 → 1.35초`

재무점수·내부자통계·애널리스트 목표가·공매도·실적일정은 서로 의존하지 않는데
순차로 실행됐다. `ThreadPoolExecutor(max_workers=5)` 로 동시 실행.

⚠️ **조용한 성능저하 방지 가드**: 이 5개는 `@st.cache_data` 함수라 워커
스레드에서 ScriptRunContext 부재로 실패할 수 있다. 그 경우 값이 전부 None 이
되어 **합류점수가 말없이 낮게** 나온다. 판정이 틀어지는 건 느린 것보다 훨씬
나쁘므로, 전부 비면 메인 스레드에서 순차로 다시 받는다. 폴백이 돌면 계측
패널에 `순차 폴백(병렬 결과 없음)` 으로 표시된다.
(실측 결과 폴백은 발생하지 않았다 — 스레드에서 정상 동작 확인)

**(B) 회사정보 — 독립 2개만 병렬화** `2.25초 → 감소`

`_fmp_fill` 과 `_fmp_profile` 은 독립이라 동시 실행.

⚠️ **같은 함수의 '다음 실적 발표일' 4단계는 일부러 병렬화하지 않았다.**
`if not next_earnings:` 폴백 체인이라 앞이 성공하면 뒤를 아예 부르지 않는다.
병렬화하면 불필요한 콜만 3개 늘고 FMP 한도를 낭비한다.

**결과**: 계측 구간 합계 8.42초 → 6.62초.

## 3. 포트폴리오 매도 레이더 (핵심)

**(A) 유니버스 랭킹을 자동화 스냅샷 읽기로 전환** `111.67초·376콜 → 3.40초·47콜`

`build_portfolio_sell_radar_df` 가 `cached_etf_universe_rankings_full` 로
**ETF 유니버스 전체(~350종목)** 를 다시 계산했다. 용도는 표시용 순위 열 하나뿐.
내부는 이미 8워커 병렬이지만 376콜 ÷ 300/분 = 최소 75초는 레이트리밋 대기라
병렬화로는 줄일 수 없었다.

자동화(`run_hidden_alpha`, 토요일 5PM)가 이미 계산해 `HiddenAlpha_Snapshot`
A1 셀에 저장하므로 앱은 읽기만 한다(1콜).

⚠️ **스냅샷은 Top 30만 담는다**(자동화가 Δ 계산용으로 그렇게 저장).
그대로 갈아끼우면 31위 밖 보유 ETF 가 「순위 산출 불가」로 표시되어, 순위를
못 구한 건지 순위가 낮은 건지 구분이 사라진다. 매도 판단에 쓰는 정보다.
→ 스냅샷이 있는데 티커가 없으면 **「🔴 30위권 밖」** 으로 표시한다.

⚠️ **주 1회 갱신**이므로 표 아래에 기준일을 명시한다. 며칠 지난 순위를
최신으로 오해하지 않도록 숨기지 않는다. 주 단위로 움직이는 모멘텀 순위라
이 신선도는 용도에 맞다.

부수 효과: 기존 TTL 1시간 캐시가 만료될 때마다 350종목을 재조회해 **1시간마다
다시 3분**이 되던 문제도 사라졌다.

**(B) 보유 종목 일봉 병렬 프리페치** `_pf_prefetch_histories()` 신설

계좌별 루프가 종목마다 600봉을 순차로 받았다. 사전에 병렬로 받아두면 루프는
전부 캐시 히트가 된다. 실측 24종목 × 600봉 = 1.67초.

⚠️ `analyze_ticker` 는 계좌 루프에서 **순차로 남겼다**. `entry_price` ·
`entry_date` 가 행마다 달라 캐시가 안 되고, `regime_core`(매수/매도 판정 SSOT)를
스레드에 태우면 검증 부담이 커진다. 실측 CPU 는 0.93초로 저렴하다.

**(C) `cached_quote_type` 병렬화**

`{t: cached_quote_type(t) for t in unique_holdings}` 순차 컴프리헨션이었다.
전멸 시 순차 폴백 가드 포함 — quote_type 이 비면 ETF/개별주 구분이 틀어진다.

**결과**: 계측 구간 합계 115.90초 → **6.00초**.

## 4. 50종목 확장 안전성 검증

보유가 25 → 50종목으로 늘어도 FMP Starter 300/분을 넘지 않는지 실측했다.

```
20콜 / 한도 5 / 8워커 → 임의 1초창 최대 5콜
병렬에서도 한도 강제: OK
```

`fmp_extras` 의 락 기반 슬라이딩 윈도우가 병렬에서도 정확히 강제한다.
워커 상한은 8로 고정하고 종목 수가 적으면 자동 축소한다.

## 7. 남은 한계 / 후속 과제

- **미계측 100콜은 백그라운드 프리워밍**(VIX·거시지표·DRG·섹터 ETF)이다.
  `_trigger_background_warmup()` 이 로그인 직후 별도 스레드로 실행하며
  세션당 1회, 화면을 막지 않는다. **정상 동작**이므로 손대지 않았다.
  FMP 카운터가 프로세스 단위라 계측에 계속 섞여 나온다.
- **정밀검사 첫 로드 ~20초** 잔존. 계측된 6.62초 외에는 프리워밍과 미계측
  영역이다. 더 줄이려면 지연 로드(어닝콜·의회거래·기관보유를 expander 를
  펼칠 때만 호출)가 다음 후보 — 시간 기여는 1초 미만이지만 종목당 5~6콜이
  줄어 연속 조회 시 한도에 도움이 된다.
- **탭 복귀 재실행 억제는 하지 않았다.** `×2` 로 보이던 것은 두 방문의 합계이며
  `@st.cache_data` 덕에 두 번째는 사실상 0초다. 이미 해결된 상태라 세션 상태만
  복잡해진다. (이전 제안 철회)
- **포트폴리오 지표 사전계산(2단계)은 보류.** 병목이 I/O 에서 제거되어 남은
  CPU 가 0.93초뿐이다. 보유가 50종목으로 늘어 CPU 가 커지면 그때
  `Watchlist_Metrics` 확장을 검토한다. 다만 포트폴리오는 `entry_price` 의존
  계산이 섞여 있어 공용 부분과 개인화 부분의 분리 설계가 선행돼야 한다.
