## 🔴 고치는 문제 — 침묵의 구멍

가격 이력이 빈 배열로 오면 평가 루프가 `continue` 로 **조용히 건너뛴다.**
로그에도, 메일에도, 앱에도 아무 흔적이 없다.

조사 결과 침묵 지점이 **1곳이 아니라 5곳**이었다.

| 위치 | 루프 | 침묵의 결과 |
|---|---|---|
| 705 | 지표 프리컴퓨트 | 표시 지표 누락 |
| 823 | 워치리스트 EOD | 매수 기회 상실 |
| **912** | **보유 EOD** | 🔴 **매도 신호 영구 침묵** |
| 1002 | 워치리스트 장중 | 잠정 헤드업 누락 |
| 1073 | 보유 장중 | 잠정 헤드업 누락 |

**912 가 진짜 구멍이다.** 보유 종목이 빈 이력을 받으면 손절·익절 신호가 아예
오지 않는다. 티커 변경·상장폐지가 흔한 원인이고, 둘 다 사전 통보 없이 일어난다.

## 🔴 설계 중 발견 — 침묵을 알리는 경로가 같은 이유로 침묵한다

`dispatch_radar_emails._send_one_user` 에 이 게이트가 있다.

```python
if not _n_u:
    print(f"[RADAR] '{uid_s}' 발동 0건 — 발송 생략.")
    return
```

`main()` 에도 같은 성격의 게이트가 하나 더 있다(`if total:`).

**미수신만 있고 발동 건이 없으면 메일이 아예 나가지 않는다.** 침묵을 알리려는
기능이 정확히 같은 이유로 침묵한다. 이걸 처리하지 않으면 기능이 무의미하다.

두 게이트 모두 미수신을 합산하도록 고쳤다.

## 범위 — EOD 2곳만

5곳 중 **823(워치리스트 EOD) · 912(보유 EOD)** 만 계측한다.

- **705(지표)** 는 알림이 아니라 표시용 백필이다. 앱에 실시간 계산 폴백이 있다

즉 실제 위험 지점만 계측하고 중복 보고를 피한다.

## 왜 '연속 N일' 이 아니라 '비율' 인가

일시적 API 장애로 여러 티커가 한꺼번에 빌 수 있다. 그걸 종목별 경고로 쏟으면
메일 폭탄이 된다. 억제 조건이 필요하다.

`연속 N일` 은 판별력이 좋지만 **상태 저장이 필요해서 시트 쓰기가 생긴다.**
Watchlist 의 `Alert_LastState` 에 얹는 것은 침습적이고, 새 시트를 파면 매 실행
읽기·쓰기가 붙는다. **로딩 시간을 늘리지 않는다는 제약과 충돌한다.**

비율은 상태 없이 같은 판별을 한다.

    미수신이 소수  → 종목 문제 (티커 변경/상장폐지)  → 개별 나열
    미수신이 다수  → API 장애                        → 한 줄 요약

    _NODATA_RATIO_ALERT = 0.30   # 초과 시 광범위
    _NODATA_MIN_SAMPLE  = 5      # 표본 미달이면 비율이 무의미 → 개별 보고

**시트 쓰기 0 · FMP 추가 호출 0.** 이미 실패한 조회의 결과를 주워 담을 뿐이다.

## 검증

### 🔴 뮤테이션 테스트가 이번엔 테스트 자체의 약점을 잡았다

M4(라벨 덮어쓰기)가 처음에 **검출되지 않았다.** 원인은 코드가 아니라 **오라클이
약한 것**이었다.

```python
return len(got) == 1 and "보유" in got[0][1]   # ✗ 약함
```

병합 버그를 심어도 마지막 호출이 `"보유"` 라서 덮어쓴 결과가 `["보유"]` 가 되고,
`"보유" in 라벨` 조건은 그대로 통과한다. **두 라벨이 모두** 남았는지 봐야 한다.

```python
return (len(got) == 1
        and "보유" in got[0][1]
        and "워치리스트" in got[0][1])       # ✓
```

이게 중요한 이유: 같은 티커가 워치리스트·보유 양쪽에 있을 때 `"보유"` 표시가
사라지면 **심각도 정보가 소실된다.** 사용자는 "매수 기회 놓쳤네" 로 읽고
"매도 신호가 안 오고 있다" 를 놓친다.
