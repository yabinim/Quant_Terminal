perf(watchlist): 알림 부분 재평가 + 일봉 병렬 프리페치로 저장 후 대기 10초→1초 내외

1차 작업(Sheets 핸들 캐시)으로 시트 왕복은 15콜 0.6초까지 줄었으나, 실사용 체감은
여전히 10초를 넘었다. 계측 패널이 "Sheets 3콜 / 0.6초"를 보여줘 병목이 시트가
아님을 곧바로 확인했고, 남은 시간이 워치리스트 알림 재평가 루프에 있음을 특정했다.

## 1. 원인

`app.py` 알림 체크 블록이 워치리스트 전 종목을 **순차 루프**로 돌았다.

```python
for _it in _wl_items:                           # 55종목
    _hist = _fmp_price_history(_tk, limit=252)  # 종목당 FMP 1콜 (순차)
    _an2 = rc.analyze_ticker(_hist, ...)        # 종목당 레짐 분석
```

그리고 `add_to_watchlist` / `delete_from_watchlist` / `update_watchlist_row` 가 모두
`_watchlist_alert_checked = False` 로 **전체 플래그를 내렸다**. 목표가 하나만 고쳐도
55종목 전체 재평가가 돌았다는 뜻이다.

`_fmp_price_history` 는 `scanner_core.ttl_cache(ttl=1800)` 로 캐시되지만 **프로세스
수명** 캐시라, 배포 직후 Streamlit 재부팅으로 완전히 비어 있었다.
55종목 × 150~250ms ≈ **8~14초** — 실측 체감치와 일치한다.

이 비용은 이번 변경이 만든 것이 아니라 원래 있었고, 그동안 Sheets 7초에 가려져 있었다.

## 2. 파일별 변경

### `app.py`

**(1) 알림 재평가를 전체 → 해당 티커 단위로 축소**

- `_wl_mark_alert_recheck(ticker)` 신설. 쓰기 3함수가 전체 플래그를 내리는 대신
  `_wl_alert_recheck` 집합에 티커만 담는다.
- 알림 블록을 **full / partial 2모드**로 재작성.
  - full: 세션 최초 1회. 전 종목 평가.
  - partial: 편집 발생 시. 표시된 티커만 평가하고 나머지 결과는 유지.
- partial 모드는 대상 티커의 **옛 결과를 먼저 걷어낸다**. 삭제된 종목이라 평가 대상이
  비더라도 묵은 알림이 남지 않도록 무조건 수행한다.
- 전체 리셋은 두 곳에만 남긴다 — 수동 「🔄 Alert 조건 다시 체크」 버튼과 워치리스트
  전체 삭제. 둘 다 전체 재평가가 의미상 맞다.

→ 편집 시 FMP **55콜 → 1콜**.

**(2) `_wl_prefetch_histories()` — 일봉 병렬 프리페치**

세션 최초 1회는 전 종목을 봐야 한다. `ThreadPoolExecutor(max_workers=8)` 로 일봉만
미리 채우고, 이후 루프는 전부 TTL 캐시 히트가 되게 한다.

- **병렬화는 네트워크 I/O 에만 적용**한다. `rc.analyze_ticker` 는 순차로 남겼다.
  레짐 엔진을 스레드에 태우는 건 검증 부담이 크고, 느린 쪽은 어차피 I/O 다.
- `max_workers=8` 은 앱의 기존 병렬 구간(4·8·11)과 같은 수준. FMP Starter 300/분
  한도 안이며, "스캐너·Hidden Alpha 와 동시 실행 금지" 운영 원칙은 그대로 유효하다.
- 병렬 실패 시 순차 폴백 — 느릴 뿐 결과는 동일하다.

→ 최초 로딩 55종목 순차 10초 → **2초 내외**.

**(3) FMP 호출 계측 추가**

`requests.get` 을 1회 래핑(멱등)하고 URL 호스트로 FMP 만 걸러 집계한다.
`fmp_extras` · `scanner_core` · `app.py` 가 모두 호출 시점에 `requests.get` 을
조회하므로 모듈 속성 하나로 전 경로가 잡힌다. Gemini·FRED 는 호스트가 달라 안 센다.

⚠️ **Sheets 와 달리 프로세스 수준 카운터**를 쓴다(`threading.Lock` 보호).
일봉 프리페치가 워커 스레드에서 도는데 거기서는 `st.session_state` 접근이 불가능해,
세션 단위로 세면 병렬 호출이 통째로 누락되기 때문이다.

사이드바 패널을 「🔧 Sheets 호출 계측」 → 「🔧 호출 계측」으로 바꾸고 Sheets·FMP를
함께 표시한다.

### `automation/diag_watchlist_writepath.py`

부분 재평가 마킹 검증 추가: 수정 시 해당 티커만 표시되는지, 전체 플래그가 내려가지
않는지, 연속 수정 시 대상이 누적되는지.

## 3. 기각한 대안

**기각 — 레짐 분석까지 병렬화 (추가 1~1.5초 절감)**
`rc.analyze_ticker` 는 `regime_core` SSOT 이고 매수/매도 판정의 핵심이다.
스레드 안전성을 검증하지 않은 채 병렬에 태우면 조용한 오판정 위험이 생긴다.
I/O 병렬화만으로 이미 대부분을 회수하므로 **하지 않는다.**

**기각 — 편집 시 알림 재평가를 아예 생략 (FMP 0콜)**
목표가·손절가를 바꾸면 그 종목의 알림 조건은 실제로 달라진다. 재평가를 건너뛰면
방금 설정한 값이 화면에 반영되지 않는다. 1콜은 쓰는 게 맞다.

**기각 — `ttl_cache` TTL 연장 (30분 → 수시간)**
콜드 스타트 빈도는 줄지만 시세 신선도가 떨어진다. 손절·목표가 알림이 묵은 가격으로
판정되는 건 손실 방지 철학에 어긋난다. **TTL 유지.**

## 5. 배포 순서 (lockstep)

`app.py` 단일 파일. 공유 코어 모듈과 자동화 7종은 변경 없음.

1. `app.py` → 저장소 루트 덮어쓰기
2. `automation/diag_watchlist_writepath.py` → 덮어쓰기 (검증 항목 추가분)
3. Streamlit 재부팅

## 7. 남은 한계 / 후속 과제

- **최초 세션 로딩은 여전히 2초 내외 소요.** 55종목 일봉은 어차피 받아야 한다.
  더 줄이려면 알림 평가를 자동화(`run_watchlist_alerts`)에만 맡기고 앱은 시트에 적힌
  결과만 읽는 구조로 바꿔야 한다 — Earnings_Calendar 에서 이미 쓰는 패턴이다.
  다음 후보로 기록해 둔다.
- **포트폴리오·매도 경로 미적용(3안 범위).** `replace_user_portfolio_sheet_rows` 는
  여전히 `ws.clear()` 후 전 사용자 행 재작성. 매도 레이더도 종목 수만큼 FMP 를 부른다.
  이번 두 패턴(핸들 캐시 + 부분 갱신 + 병렬 I/O)을 그대로 확장할 수 있다.
- **FMP 계측 시간은 병렬 시 스레드별 소요의 합**이라 체감 대기보다 크게 나온다.
  호출 '횟수' 가 진단에 더 유용하다.
- **FMP 계측은 프로세스 전체 기준**이라 게스트 사용분도 합산된다. 관리자 진단 용도로는
  무방하나, 정확한 단독 측정이 필요하면 다른 사용자가 없는 시간대에 하는 게 좋다.
