perf(watchlist): 표시 지표를 자동화 사전계산으로 이관 — 리런당 analyze_ticker 55회 → 0회

앱 지연의 마지막 축이던 CPU 재계산을 제거한다. 워치리스트 탭이 리런마다 전 종목에
`rc.analyze_ticker`(레짐+타이밍+청산신호)를 돌리던 것을, 자동화가 마감 후 미리 계산해
`Watchlist_Metrics` 시트에 적어두고 앱은 읽기만 하도록 바꿨다.

---

## 1. 배경 — 병목의 이동

| 라운드 | 조치 | 남은 병목 |
|---|---|---|
| 1 | Sheets 핸들 캐시 + 제자리 수정 (15콜→3콜) | FMP 순차 호출 |
| 2 | 알림 부분 재평가 + 일봉 병렬 프리페치 | **CPU 재계산** |
| 3 (이번) | 지표 사전계산 이관 | — |

2라운드 후 계측이 `Sheets 3회 / 0.5초`, `FMP 0회`를 보여줬는데도 10초가 걸렸다.
FMP 0회가 결정적 단서였다 — 네트워크가 아니라 순수 CPU였다.
`app.py` 워치리스트 표시 루프가 55종목 × `analyze_ticker` 를 리런마다 재계산했고,
가격은 캐시했지만 **계산 결과에는 캐시가 없었다**.

캐시로 덮는 안도 검토했으나, 종목이 100개가 되면 콜드 스타트가 다시 20초가 된다.
근본안(사전계산 이관)으로 진행했다.

## 2. 설계

### 무엇을 옮기고 무엇을 남겼는가

- **옮김 — 느리게 변하는 일봉 파생**: RSI · MA200 · ATR · 120일 고점 · 레짐 · 타이밍 ·
  청산신호 · 매수결정키. 장중에 거의 움직이지 않는다.
- **남김 — 빠르게 변하는 현재가**: `fetch_latest_prices_for_tickers`(ttl=60) 그대로.
  등록 시 대비 수익률, 손절·목표가 도달 판정은 실시간을 유지한다.

이 분리가 설계의 핵심이다. 손실 방지 도구에서 가격 기반 판정을 묵은 값으로 하면 안 된다.

### 데이터 소유 (다중 사용자)

`Watchlist_Metrics` 는 **티커 단위**다. NVDA의 RSI는 모든 사용자에게 같으므로
per-user 데이터가 아니다. 자동화가 전 사용자 워치리스트의 **합집합**을 한 번만
계산하고, 게스트는 그대로 읽는다. 이 시트에는 어떤 개인 데이터도 들어가지 않는다.

### 신선도 규칙 — 시계가 아니라 거래일 기준

```
fresh ⟺ stored.Trade_Date >= last_completed_session
```

`last_completed_session` = 오늘(ET)보다 앞선 마지막 봉 날짜.

**왜 이 규칙인가 (중요):** FMP EOD 일봉은 장중에 **당일 미완성 봉을 포함**한다.
"마지막 봉 날짜와 정확히 일치"로 잡으면, 자동화가 5PM 에 쓴 계산본이 다음 날 개장
순간 전부 낡음이 되어 장중 내내 폴백이 터진다. 사용자의 실제 사용 시간대가 미국
장중(스크린샷 23:57·03:21 KST = 10:57·14:21 ET)이라 개선 효과가 통째로 사라진다.

`>=` 인 이유는 장 마감 후 자동화 직후 구간 때문이다. 저장본의 Trade_Date 가 기준일보다
하루 앞서므로 등호만 쓰면 그 구간이 낡음이 된다.

### 스키마 — `Watchlist_Metrics` (12열)

| 열 | 내용 |
|---|---|
| A `Ticker` | 키 |
| B `Trade_Date` | 계산에 쓰인 마지막 봉 날짜 — **신선도 판정 기준** |
| C `Updated_At` | 계산 시각(ET) |
| D~K | `RSI` `MA200` `ATR` `High_120` `Last_Close` `Dec_Key` `Regime` `Timing` |
| L | `Payload_JSON` — `analyze_ticker` 전체 dict |

D~K 를 별도 열로 둔 것은 시트를 직접 열어 눈으로 확인하는 워크플로를 유지하기 위해서다.
앱이 읽는 본체는 L열이다.

## 3. 파일별 변경

### `watchlist_metrics_core.py` (신규, 저장소 루트)

계산·직렬화 SSOT. `app.py` 와 `run_watchlist_alerts.py` 가 함께 임포트한다.
이걸 분리하지 않으면 앱과 자동화가 갈라지는데, 그게 정확히 SSOT 규칙이 막으려는
실패 모드다.

- `compute_metrics()` / `to_row()` / `from_row()` / `is_fresh()` / `last_completed_session()`
- RSI 는 `rc.compute_rsi` 사용. `app.py` 의 `calculate_rsi`(scanner_core)와 동일한
  단순 롤링 평균 방식이며(compute_rsi 독스트링에 명시), 자동화가 `scanner_core` 를
  임포트하지 않아도 되게 한다. **의존은 `regime_core` 하나뿐이다.**
- 의존성: `json` `math` `numpy` `pandas` `regime_core`

### `run_watchlist_alerts.py`

- `persist_watchlist_metrics()` 추가. EOD 모드 이메일 발송 **뒤에** 호출한다 —
  저장이 실패해도 알림 전달에는 영향이 없게.
- 이 스크립트는 이미 평가 과정에서 `hist_cache` 를 채우므로 **네트워크 추가 비용이
  사실상 없다**. 중복 티커는 한 번만 계산한다(현재 평가 루프는 사용자-행 단위라
  같은 티커를 여러 번 계산하고 있었다).
- 실패해도 예외를 밖으로 던지지 않는다. 앱에 실시간 폴백이 있어 느려질 뿐이다.

### `app.py`

- `load_watchlist_metrics()` — 시트 → `{TICKER: metrics}`, `@st.cache_data(ttl=300)`.
  티커 단위 공용이라 `user_id` 를 캐시 키에 넣지 않는다.
- 표시 루프 재작성: 신선한 저장본은 그대로 사용, **낡았거나 시트에 없는 종목만**
  `wm.compute_metrics()` 로 실시간 계산(폴백). 폴백도 같은 SSOT 함수를 쓴다.
- 일봉은 `_wl_prefetch_histories()` 로 병렬 수급(매수 카드가 여전히 `hist` 를 요구).
  기존 순차 호출을 대체한다.
- 지표 출처 캡션 추가 — 기준일·저장본/실시간 종목 수·자동 갱신 시각을 항상 표시.
  어떤 봉 기준의 판정인지 숨기지 않는다.

### `automation/diag_watchlist_metrics.py` + 워크플로 (신규)

합성 일봉 기반 회귀 테스트. 네트워크·시트·Streamlit 없이 돈다.

## 4. 설계 트랩과 처리

**① NaN 은 유효한 JSON 이 아니다**
`analyze_ticker` 출력의 결측 숫자는 전부 NaN 이고 소비자(`build_buy_card` 등)가
`pd.notna` / `float()` 로 다룬다. `null` 로 보내면 `float(None)` 에서 터지거나 조용히
다른 분기를 탄다. → 전용 토큰(`__nan__`)으로 왕복시키고 복원 시 `np.nan` 으로 되돌린다.
왕복 무결성을 재귀 비교로 검증한다.

**② 열 정밀도가 곧 앱↔자동화 값 차이 (테스트가 잡아냄)**
RSI 를 소수 2자리로 저장했더니 저장본과 실시간 폴백값이 미세하게 갈렸다. 앱이 D열을
그대로 읽기 때문이다. → 4자리로 수정. **회귀 테스트가 없었으면 못 잡았을 항목이다.**

**③ 신선도 규칙 (위 2절 참조)** — 장중 미완성 봉 때문에 종일 폴백이 터지는 문제.

**④ 신규 종목 공백** — 방금 추가한 종목은 시트에 없다 → 그 종목만 실시간 폴백.

**⑤ 시트 미존재** — 자동화가 아직 안 돈 상태면 빈 dict → 전 종목 실시간 계산.
기능은 정상, 속도만 종전과 같다. 캡션으로 안내한다.

## 7. 배포 후 확인 절차

**즉시 (자동화 전)**
- 워치리스트 탭 진입 → 캡션에 "지표를 실시간 계산했습니다" 표시가 정상.
  아직 시트가 없으므로 속도는 종전과 같다.

**첫 EOD 자동화(평일 5PM ET) 이후**
1. Google Sheets 에 `Watchlist_Metrics` 탭 생성 확인. 행 수 = 워치리스트 고유 티커 수.
   `Trade_Date` 가 당일, `Regime`·`Timing` 열이 채워졌는지 눈으로 확인.
2. 앱에서 사이드바 「🔧 호출 계측」 초기화 → 워치리스트 탭 재진입
3. 기대치: 캡션에 `지표 기준일 YYYY-MM-DD · 저장본 55종목`, **실시간 계산 0종목**
4. 체감 로딩이 10초 → 1초 내외

**이상 신호**
- "실시간 계산 55종목" → 신선도 판정 실패. `Trade_Date` 값 확인 필요.
- 레짐/타이밍이 개별종목 탭과 다름 → SSOT 불일치. 즉시 보고.

## 8. 남은 한계 / 후속 과제

- **콜드 스타트 ~2초 잔존.** `build_buy_card` 가 여전히 `hist` 를 요구해 일봉 55종목을
  받아야 한다. 없애려면 `build_buy_card` 에 `levels` 인자를 추가해야 하는데, 이는
  `regime_core`(매수/매도 판정 SSOT) 수정이라 전 호출부 회귀가 필요하다. 프로세스당
  1회 발생하는 2초라 **보류**했다. 계측치 보고 판단.
- **지표는 하루 1회(EOD) 갱신.** 일봉 파생이라 장중 변동이 미미하다는 전제다. 다만
  갭 상승·급락 당일에는 전일 종가 기준 레짐이 표시된다. 캡션의 기준일 표기로 이를
  명시하며, 가격 기반 알림(손절·목표가)은 실시간이라 영향받지 않는다.
- **intraday 모드는 저장하지 않는다.** 2PM 실행 시점의 미완성 봉으로 계산한 값을
  저장하면 확정 봉 기준과 섞인다. EOD 확정분만 신뢰한다.
- **포트폴리오·매도 레이더 미적용.** 같은 구조(종목 수만큼 `analyze_ticker`)를 쓰므로
  동일 패턴을 확장할 수 있다. 다음 후보.
