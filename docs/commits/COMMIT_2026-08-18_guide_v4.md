## 1. 사실과 달랐던 것 — 워크플로 yml 과 대조해 수정

자동 이메일 스케줄 표가 실제 실행과 달랐다. `.github/workflows/*.yml` 을 직접 대조했다.

| 시간 | 가이드(v3) | 실제 |
|---|---|---|
| 평일 5pm | 내러티브 + DRG 검증 + 매매 레이더 | **+ `run_earnings_watch`** (4개) |
| 주말 5pm | 주간 내러티브 + Hidden Alpha | **+ `run_scanner_scan`, `run_weekly_report`** (4개) |

새 표에는 실행 스크립트명을 함께 적었다. 다음에 스케줄이 바뀌면 대조가 쉬워진다.

**표준 워크플로우 표**에 ⓪ 시작 · ⑥ 실적 확인 · ⑨ 청산(사유 태그)을 넣었다.

**손 루틴**에 진입 시점을 명시했다 — 백테스트 진입가 규칙이 `close[t+1]` 이므로
신호 당일이나 애프터아워스에 사면 성과 수치와 실행이 어긋나 대조가 불가능해진다.

## 2. 아예 빠져 있던 탭 4개

가이드가 17개 메뉴 중 12개만 다루고 있었다.

- **🏠 시작** — 왜 만들었는지(28.7초 → 4초, 원인은 워치리스트 점검 24.3초),
  알림 확인 버튼을 안 눌러도 놓치지 않는 이유, 기동 계측 표
- **📅 실적 레이더** — radar-only 모드인 이유, 지연 계산 구조, 예상 변동폭이
  방향 정보가 아니라는 것, A/B/C 블록, 트랜스크립트 402, 내부자 블록의 미검증 상태
- **⚙️ 내 설정** — 알림 토글(관리자도 예외 아님), 계좌 프로필, DRIP
- **👑 관리자** — 유저 승인 + 개발 리마인더(연기가 만기를 이기는 이유,
  빈 블록을 안 붙이는 이유, What_To_Check 를 실행 지시로 쓰라는 것)

## 3. 기존 탭에 추가

- **💵 매도 기록 — 사유 태그** — `[매도:]` 와 `[판정:]` 을 분리한 이유.
  둘이 어긋난 경우가 실행 갭이고, 뭉개면 엔진 문제와 실행 문제를 구분할 수 없다

## 4. FAQ 5개 추가 (10 → 15)

- 로그인하면 왜 DRG가 아니라 시작 화면인가 (계측 수치 포함)
- 알림 확인 버튼을 꼭 눌러야 하나 (아니오, 3중 안전장치)
- 실적 레이더 판정을 왜 따로 계산하나 (+ 자동화 사전계산을 안 쓴 이유)
- 매도할 때 사유를 왜 고르나
- 알림 받은 당일·애프터아워스에 사면 안 되나

## 5. 게스트 가이드도 갱신

게스트가 쓸 수 있는 범위만 반영했다.

- 🏠 시작 화면 도착 + 알림 버튼 설명
- 워크플로에 실적 확인·매도 사유 단계 편입
- 자유 사용 탭 표에 📅 실적 레이더 추가
- 실적 레이더 사용법 · 매도 사유 고르는 법 신설
- 이메일 설명 수정 — 매매 레이더는 **발동 건이 없으면 아예 안 온다**(누락 아님),
  스캐너 결과 항목 추가
