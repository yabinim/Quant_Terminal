feat(industry): 업종 모멘텀·백분위 데이터 계층 (D 1단계)

## 무엇을 위한 것인가

Phase 3 정밀진단에 **"이 종목의 업종이 149개 중 어디쯤인가"** 를 붙이기 위한
데이터 계층이다. 이번 차수는 **데이터만** 만들고 화면은 다음 차수다.

화면을 분리한 이유: 시트에 데이터가 없으면 표시 로직을 테스트할 수 없고,
`app.py` 는 A-2a 배포 대기 중이라 지금 건드리지 않는 것이 안전하다.

## 왜 신호가 아니라 정보인가

백테스트(`diag_industry_momentum`) 결과가 갈렸다.

    ① 무작위 대조군   ✅ 무작위 30회 중 1회만 최고 설정을 이겼다
                         → **순위에 정보가 있다**
    ② 워크포워드      🔴 전반 1위가 후반에 동일가중 대비 -15.3%
    ③ 반분할          🟠 1/8
    ④ MDD             🔴 0/18 (다만 집중 전략에 불리한 기준이었다)

정보는 있는데 **거래 규칙으로 전환되지 않았다.** 그래서 보여주기만 하고 매매
판정에는 연결하지 않는다. 연결은 롤링 워크포워드가 통과한 뒤에 다시 본다.

참고로 섹터(11개)는 ①마저 실패했다(무작위 6/30). 최고 설정이 섹터 +14.4% vs
업종 +84.2%. **세분화가 실제로 의미 있었다** — "섹터부터 해보자"는 앞선 권고가
데이터로 틀렸음이 확인됐다.

## 🔴 설계 중 정정 — 스냅샷만으로는 안 된다

`industry-performance-snapshot` 은 **하루치 변화율**이다. 모멘텀이 아니다.

하루 등락으로 149개를 줄 세우면 그냥 잡음이다 — "상위 8%"가 내일 "하위 30%"가
된다. 앞서 "일 1콜이면 충분"이라고 한 것은 틀렸다.

20일·120일 누적이 필요한데 매일 API 로 받으면
`historical-industry-performance` **149콜/일**이 든다. 불가능하다.

→ **히스토리를 직접 쌓는다.**

    ① 일회성 백필   historical-industry-performance × 149콜 → 754행
    ② 매일 1콜      industry-performance-snapshot → 1행 append
    ③ 모멘텀 계산   시트에서 산출 (API 호출 0)

유지비가 하루 1콜이다. 백필은 백테스트에서 이미 받아본 데이터라 재활용이다.

## 시트 형식 — 왜 와이드인가

    Date        | Advertising Agencies | Aerospace & Defense | ... (149열)
    2023-08-21  | 0.42                 | -1.13               | ...

롱 포맷(날짜·업종·값 3열)이면 149행/일 × 754일 = **11만 행**이다.
와이드는 **754행**이다. 셀 수는 같지만 Sheets 는 행 수에 훨씬 민감하다.

⚠️ 열 순서는 **헤더가 SSOT**. 새 업종이 생겨도 기존 열을 밀지 않고 끝에 붙인다.
   밀면 과거 데이터가 통째로 어긋나는데, 그건 조용히 일어나고 되돌리기 어렵다.

## 변경 내역

### `industry_core.py` (신규, repo root)

`reminders_core` / `calendar_core` 패턴 — **모듈 레벨에서 gspread 를 import
하지 않고**, `requests` 도 함수 안에서 지연 import 한다. `app.py` 가 다음
차수에 흡수해도 임포트 비용이 붙지 않게 하기 위함이다.

| 함수 | 역할 |
|---|---|
| `parse_perf_values(values)` | 와이드 시트 → 구조화 (순수, gspread 무관) |
| `build_row(header, records, date)` | 스냅샷 → **헤더 순서** 1행 + 신규 업종 보고 |
| `momentum(series, lookback, end)` | 복리 누적. 결측 30% 초과면 None |
| `rank_percentile(mom_map)` | 상위 백분위(작을수록 좋음), 동점 처리 |
| `compute_ranks(parsed)` | 20일·120일 + `DIRECTION_LAG` 전 백분위 |
| `describe(rank_row)` | `상위 8% (↑ 1주 전 24%)` |
| `fetch_*` | FMP 조회 (자동화 전용) |

설계 상수:

    LOOKBACKS = (20, 120)    백테스트에서 전 구간 최고는 LB20, 반분할을
                             유일하게 통과한 건 LB120 이었다. 어느 쪽이
                             맞는지 모르므로 둘 다 보여주고 관찰한다.
    DIRECTION_LAG = 5        방향 표시용. "지금 좋은 것"보다 "올라오는 중"이
                             초기 수혜주 발굴 철학에 맞다.
    MIN_COVERAGE = 0.70      결측이 많으면 순위를 신뢰하지 않는다.
                             159개 중 10개는 아예 데이터가 없다.

### `automation/refresh_industry_perf.py` (신규)

백필과 일일 append 를 **한 파일**에 뒀다. 둘 다 같은 헤더 규약을 다루는데,
파일을 나누면 규약이 두 곳에 생기고 어긋나면 과거 데이터가 밀린다.

    --backfill   149콜, 시트 전체 재구성 (일회성)
    (기본)       1콜, 1행 append (매 평일)

안전장치:
- 휴장일 행 제거 (`calendar_core`) — FMP 는 휴장일에도 행을 준다(3년 +23행)
- 같은 날짜가 이미 있으면 **중복 append 안 함** (워크플로 재실행 안전)
- 신규 업종은 헤더 **끝에** 추가 (기존 열 순서 불변)
- 시트가 없으면 안내 후 종료 — 실패가 아니다

### 개발 중 잡은 것 2건

**① 방향 검사가 잘못 짜여 있었다.** 업종 3개로 검사했더니 백분위 단위가 33%p
라 순위가 움직일 여지가 없었고, RISER 가 양쪽 시점 모두 1위여서 변화가 안
잡혔다. **검사 대상이 아니라 검사가 틀렸던 것.** 업종 10개 + 급등을
`DIRECTION_LAG` 봉 안으로 옮겨 재작성했고, 하락(↓)도 함께 검사하도록 했다.

**② DRY_RUN 일일 모드가 동작하지 않았다.** `DRY_RUN` 일 때 시트를 아예 안
열게 해놨는데, 일일 append 는 **헤더를 읽어야** 행을 만들 수 있다. 리허설
자체가 불가능했고, 게다가 "시트가 없습니다" 라는 엉뚱한 메시지가 나왔다.
`DRY_RUN` 이 막는 것은 '쓰기'지 '읽기'가 아니다 — 수정.

### 🔴 백필 실행 경로 — 처음엔 빠뜨렸다

"실수로 반복 실행될까 봐" 백필용 워크플로를 만들지 않았는데, 그러면 **실행할
방법 자체가 없다.** 평일 5PM 스텝은 일일 append 만 하고, 시트가 없으면 안내만
하고 끝난다 — 데이터가 영영 안 쌓인다.

반복 실행 방지는 **버튼을 없애서가 아니라 코드가** 해야 할 일이었다.

    · `.github/workflows/refresh_industry_perf.yml` 추가 (workflow_dispatch)
    · 스크립트에 덮어쓰기 가드: 시트에 행이 있으면 `FORCE=1` 없이는 거부
    · 워크플로는 confirm 칸에 정확히 `OVERWRITE` 를 입력해야 FORCE 를 넘긴다

모드 4종: `dry_run_backfill`(기본) / `backfill` / `daily` / `dry_run_daily`.
`daily` 는 평일 워크플로가 놓쳤을 때 보충용이다.

가드 검증 4조합:

    빈 시트 · FORCE 없음        → 통과 ✅
    데이터 2행 · FORCE 없음     → 거부 ✅
    데이터 2행 · FORCE 있음     → 통과 ✅
    헤더만 · FORCE 없음         → 통과 ✅

Actions 표현식도 16조합 확인 — `confirm` 이 정확히 `OVERWRITE` 일 때만 FORCE 가
넘어간다(`overwrite` 소문자는 안 넘어감).

## 남은 한계

- **화면이 없다.** 데이터만 쌓인다. Phase 3 표시가 다음 차수다
- **백필 전에는 일일 append 가 아무 일도 안 한다.** 시트가 없으면 안내만 하고
  종료한다. 순서를 지켜야 한다
- **149개 중 10개는 데이터가 없다**(`Copper`, `Department Stores` 등).
  모집단이 149가 아니라 그날 유효한 수로 잡히므로, 백분위가 날마다 미세하게
  다른 모집단 위에서 계산된다. `n_universe` 를 함께 반환해 두었으나 화면에
  쓸지는 다음 차수에서 결정
- **모멘텀 창 2개를 그대로 노출한다.** 어느 쪽이 맞는지 모르는 상태이므로
  의도한 것이지만, 사용자가 둘을 보고 혼란스러울 수 있다
- **자동화에 SSOT 버전 검사가 없다.** `INDUSTRY_CORE_VERSION` 을 넣어 뒀으나
  확인하는 쪽이 아직 없다 (`calendar_core` 와 같은 상태)
