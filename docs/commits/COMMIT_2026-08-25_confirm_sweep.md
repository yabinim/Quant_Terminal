# feat(backtest): 확정 일수(CONFIRM_DAYS) 스윕 지원 + 배선 회귀 스위트

## 왜

"2일 확정이 값어치를 하는가" 를 재기 위해서다.

라이브 알림은 조건이 **이틀 연속** 참이어야 발동한다. 그 사이 가격은 움직인다.
확정을 기다리는 대가로 이틀치 가격을 지불하고 있는데, **그 지불액이 얼마인지
측정된 적이 없다.** 싸면 좋은 보험이고, 비싸면 보험료가 사고 손실보다 클 수 있다.

`walk_forward_events(confirm_days=...)` 는 이미 파라미터였다. 모듈 상수만
외부에서 조절할 수 있게 빼면, 같은 유니버스·같은 날 1/2/3 을 돌려 **확정 일수만
변수인** 비교가 된다(쿨다운·진입지연·유니버스가 전부 동일).

---

## 변경 내용

### 1. `run_signal_backtest.py` (v2.7)

**① `CONFIRM_DAYS` 를 환경변수로** — `_env_confirm_days()` 신규.
정수 1~10 만 허용하고, 빈값·쓰레기·범위 밖은 기본 2 로 폴백한다.

**폴백은 반드시 시끄럽다(`[WARN]` 출력).** 이게 설계의 핵심이다. 입력을 3으로
주고 돌렸는데 조용히 2로 떨어지면 —

    세 번 돌려 똑같은 숫자가 나온다
      → "확정 일수는 성적에 영향이 없다" 는 **정반대 결론**
      → 로그에도 시트에도 아무 이상이 없다

90분을 쓰고 틀린 결론을 얻는다.

**② 결과 시트에 `Confirm_Days` 열 추가.** 없으면 시트에 1일·2일·3일 행이 섞였을 때
구분할 방법이 없다. `Entry_Rule` 열을 넣었던 것과 정확히 같은 이유다.

**③ 호출부가 명시적으로 전달.** `run_backtest()` → `walk_forward_events(...,
confirm_days=CONFIRM_DAYS)`.

기본 인자(`confirm_days: int = CONFIRM_DAYS`)는 **함수 정의 시점에 바인딩**되므로
현재 순서(상수 → def)로도 동작은 한다. 그러나 호출부가 아무것도 안 넘기면
"환경변수가 정말 전달됐는가" 를 정적으로 확인할 방법이 없다. 명시적으로 넘겨
AST 검사가 가능해진다.

### 2. `market_backtest_monthly.yml`

`workflow_dispatch` 입력 `confirm_days`(기본 `'2'`) → `env: CONFIRM_DAYS`.

정기 `repository_dispatch` 실행에는 inputs 가 없어 빈 값이 되고, 파이썬이 2로
폴백한다. **표현식으로 값을 만들지 않고 입력값을 그대로 넘긴다** — 선택지가
늘 때마다 고쳐야 하는 매핑은 언젠가 안 고쳐진다(2026-08-22 실제 사고).

### 3. `diag_confirm_sweep.py` + `.yml` (신규) — 33항목

| 절 | 내용 | 항목 |
|---|---|---|
| 1 | 파싱 — 정상값·빈값·쓰레기·범위밖 | P1–P14 |
| 2 | **전달 — 이벤트가 며칠째 확정되는지 직접 셈** | T1–T5 |
| 3 | 배선 — `run_backtest()` 명시 전달 (AST) | W1–W3 |
| 4 | 기록 — 행에 `Confirm_Days` 가 실리는가 | R1–R4 |
| 5 | 뮤테이션 6종 + 양성대조 | F-M1–3 · W-M1–3 · G-1 |

**2절이 핵심이다.** 1절(파싱)과 3절(배선)만 있으면 "환경변수는 읽혔고 인자로도
넘어갔는데 정작 루프가 무시하는" 경우를 못 잡는다. 그래서 가짜 `analyze_fn` 을
주입해 확정 봉 위치를 직접 센다 — confirm=1 → 300, 2 → 301, 3 → 302
(entry 시작 300). 세 값이 서로 달라야 스윕이 의미를 가진다.

G-1 양성대조가 그 판별력 자체를 확인한다: confirm 을 무시하는 러너를 만들면
T4 가 실제로 깨지는지 본다. "항상 통과하는 스위트" 방지.
