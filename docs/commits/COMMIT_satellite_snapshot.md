### 2. `automation/run_satellite_snapshot.py` (신규 · 317줄 / GitHub 316)

python automation/run_satellite_snapshot.py --seed    # 개시일 기준선 (최초 1회)

**왜 `run_hidden_alpha` 에 얹지 않았나.** 두 가지 이유다.

1. `run_hidden_alpha` 는 ISO 주 가드로 **일요일 1회**만 돈다. 월말이 화요일이면

   있으므로 문서와 코드가 처음부터 갈라진 채 시작한다.
2. `run_hidden_alpha` 에는 랭킹 산출 실패 시 `sys.exit(1)` 경로가 있다. 데이터가
   모자라 랭킹이 죽는 상황은 **시장이 나쁠 때 더 잘 일어난다.** ③이 가장 필요한
   구간에서 기록이 조용히 빠진다.

주요 동작:

- 월말 판정은 `calendar_core` 규칙 계산 (`is_market_open` + `next_trading_day`).
  FMP 콜 0 · 시트 0. 다른 날은 즉시 종료.
- 보유는 `portfolio_core.load_rows` → 관리자(`users_core.ADMIN_CONTENT_OWNER_ID`)의
  `SATELLITE_BOOKS` 두 계좌만.
- **종가를 한 종목이라도 못 받으면 `[ABORT]` 하고 아무것도 쓰지 않는다.** 부분
  기록은 그 장부를 과소 계상하고, 과소 계상은 **낙폭을 부풀려** 트리거를 앞당긴다.
  틀린 숫자가 시계열에 영구히 남는 것보다 그 달을 비우는 편이 낫다.
- `(날짜, 장부)` 중복 가드 — 재실행해도 덧쓰지 않는다.
- `--seed` 는 개시일에서 14일 넘게 지나면 `FORCE=1` 없이 거부한다. 시드는 **오늘
  보유**를 개시일 종가로 평가하므로, 그 사이 매매가 있었으면 기준선이 거짓이 된다.

**M9 는 처음에 생존했다.** `dd <= TRIGGER` → `abs(dd) >= abs(TRIGGER)` 로 바꿔도
D 군 값 검사가 아무것도 못 잡았다. 원인을 따져보니 **등가 돌연변이**였다 — 고점을
'현재 포함 최댓값'으로 잡으므로 `dd` 는 항상 0 이하이고, 그 조건에서 두 식은 같다.

지금은 같지만 영원히 같지는 않다. 고점 정의를 '직전까지의 최댓값'으로 바꾸는 날
`abs()` 형태는 **+30% 상승에서 축소를 발동시킨다.** 그래서 두 줄을 추가했다:

- **D12** — 200회 무작위 입력에서 낙폭이 양수가 되지 않는다는 불변식(전제 고정)
- **D13** — 비교식이 `abs(` 를 쓰지 않고 `<=` 를 쓴다는 소스 검사(전제가 깨진 날
  이 자리가 반드시 함께 검토되게)

**M14(`<` 로 변경)도 값 검사를 빠져나간다** — `70/100 - 1` 이 부동소수로
`-0.30000000000000004` 가 되어 `<` 로도 발동하기 때문이다. D13c 만 잡는다.
**D13 을 지우면 이 둘이 다시 조용히 통과한다.**

- **현금 미추적.** `Cash` 열은 공란이다. §4③·§6 에 명시했고 앱·메일에 매번 뜬다.
  현금을 관리하기 시작하면 열을 채우는 것만으로 한계가 사라지고, 그때 §6 ③ 을 ✅ 로
  올릴 수 있다(진단 E1 이 그 조건을 강제한다).
- **§6 ② 실행 이탈 기록은 여전히 ❌.** 이 커밋의 범위가 아니다.
- **`market_5pm_weekday.yml` 에는 락스텝 관문이 없다.** 8AM·주말 워크플로가 레포
  전체를 훑으므로 새 러너의 불일치는 거기서 잡힌다. 평일 5PM 자체에 관문을 넣는
  것은 별건이다.
