## 4. 왜 봉수를 달력일에 그대로 넣으면 안 되는가

`calendar_days_for_bars(2)` = `ceil(2 ÷ 0.6871)` = **3달력일**이다.
금요일 휴장(굿프라이데이·독립기념일 등)이면 목 종가에서 다음 월요일까지 간격만
4달력일이라 **0봉**이 온다. 비상 휴장은 더 길다 — 2001-09-11 은 7달력일 연속이었다.

그래서 순수 환산기를 호출부에서 직접 쓰지 않는다.

### 신설: `fmp_extras.HIST_MIN_DAYS = 21` · `hist_days_for_bars(bars, pad_bars=5)`

```python
def hist_days_for_bars(bars, pad_bars: int = 5) -> int:
    need = max(1, int(bars)) + max(0, int(pad_bars))
    return int(min(max(calendar_days_for_bars(need), HIST_MIN_DAYS), HIST_MAX_DAYS))
```

기존 `calendar_days_for_bars` 와 **역할을 분리**했다:

| 함수 | 역할 | 쓰는 곳 |
|---|---|---|
| `calendar_days_for_bars` | 순수 환산. 마진·하한 없음 | 무마진 최소치 계산(진단 T6) |
| `hist_days_for_bars` | 마진 + 하한 + 상한 포함 최종값 | **호출부** |

**하한 21일의 근거:** 7달력일 비상 휴장이 창에 통째로 들어와도 14달력일 ≈ 9봉이
남아 이 파일의 최대 소형 요구(6봉)를 넘긴다. 대장주 51일 창은 같은 사고에도
44일 ≈ 30봉 ≥ 20봉. 진단 `T9` 가 이 계산을 매번 다시 한다.

**왜 호출부에서 `calendar_days_for_bars(n + 5)` 로 때우지 않았나:** `0.6871` 은
한 벌이어도 **마진 정책이 5벌**이 된다. 나중에 한쪽만 갱신되고, 그 실패는 로그를
남기지 않는다. `X5b` 가 `run_drg_predict` 에서 순수 환산기 직접 호출을 금지한다.

### 비대칭 비용

- **언더슈트** → `len(rows) >= 6` 가드에 걸려 **신호가 조용히 사라진다.**
  `rolling(20, min_periods=10)` 이면 더 나쁘다 — **에러 없이** 더 짧은 창의 평균이
  나와 `below_ma20` 이 조용히 틀린다.
- **오버슈트** → 수 KB 페이로드. 관측 가능하고 되돌리기 쉽다.

마진을 이 방향으로 기울인 이유다.

## 5. 승인안에 없던 변경 2건 (변이 검증 중 발견)

### 5-1. `_fmp_hist` 의 `bars` 기본값 제거

변이 P5(`def _fmp_hist(sym, bars=30)` → `bars=6`)를 **처음에 놓쳤다.** 원인을 파보니
진단이 아니라 코드 쪽이었다:

- 대장주 호출부는 `bars=30` 을 **명시**로 넘긴다 → 기본값을 바꿔도 창이 안 변한다.
- 기본값 30 이 실제로 먹히던 곳은 **HYG/LQD(요구 6봉)** 뿐이었다.
  신용 스프레드는 자기 요구의 5배를 받고 있었고, 그 사실을 아무도 몰랐다.

즉 기본값 30 은 **우연히 맞던 값**이었다. 두 소비처의 요구가 다른데(6봉 vs 20봉)
기본값이 있으면 호출부가 자기 요구를 안 밝혀도 통과하고, **어느 요구인지 모르는
창**이 생긴다.

→ `def _fmp_hist(sym, bars):` 로 기본값을 없애고 두 호출부에 요구를 명시했다
(`bars=6` / `bars=30`). 요구를 못 밝히면 `TypeError` 로 즉시 죽는 편이 낫다.
`D0e`(정의부에 기본값 없음) · `D0f`(호출 3곳 전부 `bars` 명시)가 못 박는다.

기본값 부활은 **그 자체로는 동작을 안 바꾸므로 런타임 검사에 안 잡힌다** — 정적
검사가 필요한 이유다.

### 5-2. 응답 정렬 가정 2곳 제거

창을 21일로 줄이면 새로 생기는 위험이다. 두 곳이 FMP 의 newest-first 정렬을
**검증 없이 가정**하고 있었다:

| 위치 | 옛 코드 | 정렬이 뒤집히면 |
|---|---|---|
| `_prev_close` | `for row in rows:` 첫 비오늘 행 | 창에서 **가장 오래된** 종가가 '직전 종가'가 된다 |
| SPY 현재가 | `spy_rows[0]["close"]` | 창에서 **가장 오래된** 종가가 'SPY 현재가'가 된다 |

둘 다 **에러가 나지 않는다.** `limit` 시절에는 오차가 5년치였고, 창 축소로 오차 폭만
21일로 줄어들 뿐 결함은 그대로다. 나머지 3곳은 `set_index("date").sort_index()` 가
있어 원래부터 정렬 무관이었다.

→ `sorted(key=date, reverse=True)` 와 `max(key=date)` 로 순서 의존을 없앴다.
`D5`(oldest/newest 두 정렬에서 산출 텍스트 동일) · `D6c` 가 회귀를 잡는다.

## 6. 신규 검사군 [D] — 왜 정적 분석으로 부족한가

이 파일의 실패 모드는 **전부 조용한 값 오류**다. 셋 다 AST 로는 안 보인다:

1. 창이 짧으면 `len(rows) >= 6` 가드에 걸려 신호 한 줄이 통째로 사라진다.
2. `rolling(20, min_periods=10)` 은 20봉 미만이어도 에러 없이 더 짧은 창의 평균을 낸다.
3. 응답 정렬을 가정하면 오래된 종가가 최신 자리에 들어간다.

그래서 `[D]` 는 `run_drg_predict` 를 **실제로 임포트해 스텁 FMP 위에서 실행**한다.
`app.py` 와 달리 이 모듈은 임포트해도 UI·시트·메일이 깨어나지 않는다.

스텁은 요청된 `from`/`to` 창 안의 **평일을 봉으로 생성**한다. 창이 짧으면 봉이
실제로 모자라진다 — 창 길이를 문자열로 비교하는 게 아니라 **결과를 관측**한다.

| 검사 | 내용 |
|---|---|
| `D0a~D0f` | 배선 · `requests` 임포트 부재 · `_fmp_hist` 기본값 금지 |
| `D0-STOP` | 원시 GET 잔존 시 **런타임 검사 중단**(아래 참조) |
| `D1a~D1d` | `from`/`to` 존재 · `limit` 부재 · `to` = 오늘+1 |
| `D2a·D2b` | 관측 창이 정책 변환기 산출과 정확히 일치 |
| `D3a~D3c` | 각 창이 **그 창이 존재하는 이유(소비 깊이)** 를 덮는가 |
| `D4a·D4b` | **7달력일 연속 휴장 주입** 후에도 요구를 덮는가 |
| `D5` | oldest-first / newest-first 응답에서 산출 텍스트 동일 |
| `D6a~D6c` | `main()` 의 SPY 블록을 AST 로 떼어내 **실제 실행** |

### D0-STOP — '네트워크 0' 약속을 지키는 장치

원시 `requests.get` 이 한 곳이라도 남아 있으면 `fh` 스텁이 그 경로를 **가로채지
못하고**, 아래 런타임 검사가 진짜 FMP 로 나간다. 그래서 `D0c`/`D0d` 가 실패하면
즉시 조기 종료한다. 역검증(패치 전 파일 투입)에서 이 경로가 실제로 작동했다.

### D3 의 요구치는 어디서 오는가

요구 봉수를 저장소 어디에도 상수로 적지 않는다는 기존 원칙을 따르되, 이 파일의
소비 구문은 함수 경계를 넘어 흩어져 있어 AST 역산이 과하다. 대신 **창 → 최소 요구
봉수** 표를 진단 안에 두고 소스 주석과 짝을 맞췄다:

```
창별 최소 요구 봉수: {21: 6, 51: 20}
공급 봉수(정상)   : [(21, 16), (51, 38)]
공급 봉수(7일 휴장): [(21, 11), (51, 33)]
```

`D3b` 가 "51일 창 호출이 실제로 관측된다"를 따로 확인해 **검사기가 헛도는 것**을
막는다(호출이 하나도 없으면 `D3a` 는 공허하게 참이 된다).
